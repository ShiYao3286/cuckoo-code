# 记忆整理 Prompt 设计

> 本文档记录「用户画像自动整理」功能的 prompt 设计与**模型选型验证结论**。
> 验证时间：2026-10-19；验证方式：同一段真实对话 + 同一份 prompt，横向对比 5 个模型。

## 一、为什么需要「画像」而不是「清单」

现有记忆（035）是**扁平事实清单**：

```json
[
  { "text": "用户偏好中文", "scope": "user" },
  { "text": "测试用 vitest", "scope": "user" },
  { "text": "提交信息中文", "scope": "user" }
]
```

问题：
- **碎片化**：每条独立，无关联，越积越多（上限 200 条纯属无奈）
- **无法淘汰**：只知道「加」，不知道该删哪条
- **信息密度低**：占提示词空间，但传达的「用户是谁」很模糊

「画像」则是**结构化段落**：

```json
{
  "identity": "独立开发者，主要做 TypeScript 的 Electron 桌面应用，有开源项目维护经验。",
  "communication": "偏好简洁直接的中文回复，不喜欢冗长铺垫。",
  "engineering": "TypeScript 严格模式禁用 any；测试用 vitest 不用 jest；提交信息遵循 Conventional Commits 中文格式。"
}
```

优势：连贯、可推断、有结构、能整体重写（而非只增不减）。

## 二、核心设计：重写而非追加

这是与「事实清单」的本质区别，也是借鉴 GPT Dreaming 的核心思想：

| 模式 | 行为 | 问题 |
|---|---|---|
| 追加（append） | 新信息 push 进数组 | 越积越多、互相矛盾、无法淘汰 |
| **重写（rewrite）** | 每次输出**完整的新画像** | 能主动合并、更新、淘汰 |

因此整理管道的输入是「现有画像 + 新对话」，输出是「重写后的完整画像」。

## 三、System Prompt（生产版）

```
你是记忆整理器。把用户的历史对话合成为一份「用户画像」，供 AI 助手在后续对话中理解用户。

## 硬性格式要求（违反即失败）

- identity / communication / engineering / environment / notes：必须是一个字符串，是连贯的中文段落。
  禁止输出数组、嵌套对象、Markdown 列表、多个短句堆砌。
- projects：必须是对象，key 是项目的绝对路径（如 "E:/proj/foo"），value 是该项目的约定字符串。
  如果对话里没有明确的项目路径，projects 输出空对象 {}。
- 某节没有信息就输出空字符串 ""，不要写「无」「未知」「暂无」。

## 内容规则

1. 重写而非追加：输出是重写后的完整画像，不是增量。
2. 主动合并与淘汰：新信息与旧矛盾时以新的为准；旧信息过时则删掉。
3. 推断而非罗列：不写「用户用了 pnpm 三次」，要写「用户偏好 pnpm」。
4. 保守：不确定的不写；一次性任务细节（「帮我看这个文件」）不记。
5. 不臆造：只基于给定材料，不推测用户没表达过的偏好。
6. 不串味：身份归 identity，沟通风格归 communication，工具链/规范归 engineering，
   操作系统/路径习惯归 environment。技术栈属于 identity 或 engineering，不要塞进 communication。

## 各字段该写什么

- identity：跨项目稳定的身份——职业、技术背景、长期从事的项目类型。
  禁止写入「当前正在做什么」「关注某个功能」「想加某个特性」这类一次性任务。
- communication：只写沟通方式——语言偏好、详细程度、对反问/客套的态度。
  不要写任何工具、框架、提交规范、编码习惯。
- engineering：工程习惯——工具链、代码风格、测试框架、提交规范、目录约定。
- environment：环境约束——操作系统、shell、路径特征、编码习惯。
- projects：仅当对话中出现了明确的绝对路径才写。key 必须是路径（含 / 或 \ 或盘符），
  value 是该项目的专属约定。没有路径就输出 {}。技术栈名不是项目路径。
- notes：其他长期有用且不属于以上任何一类的信息（账号、外部服务、长期目标）。
  同一条信息只能出现在一个字段里，不要在多处重复。

## 三条铁律（违反即失败）

1. 不得虚构：只写对话里明确出现过的信息。不要根据「常见开发者习惯」补充任何内容。
2. 不得记录任务：具体的 bug 修复、功能开发、文件修改过程都不属于画像。
3. 不得重复：同一条信息只放最合适的那个字段，不要在 engineering 和 notes 里各写一遍。

## 反面示例（只说明错误形态，不要照抄内容）

✗ 把对象/数组塞进字符串字段
✗ 把技术栈名（如 "Electron"）当成 projects 的 key
✗ 把「修复 BOM 问题」这类任务细节写进 notes
✗ 同一条信息在多个字段重复出现

## 输出

严格 JSON，不要 markdown 代码块包裹：

{
  "identity": "字符串",
  "communication": "字符串",
  "engineering": "字符串",
  "environment": "字符串",
  "projects": {},
  "notes": "字符串"
}
```

**关键设计决策**：

1. **「反面示例」只描述错误形态，不写正确示例的具体内容**——早期版本写了正面示例（如「遇到模糊需求希望先提问再动手」），结果弱模型直接**照抄示例当答案**，产生了看不出是幻觉的幻觉。
2. **反复强调「不得虚构」**——弱模型会把「开发者画像应该有什么」当成事实补全。
3. **明确的字段边界**——不划定边界，模型会把提交规范塞进 communication。

## 五、模型选型验证（核心结论）

**验证方法**：同一段 314 字符真实对话 + 同一份 prompt，横向对比 5 个模型。

### 结果

| 模型 | identity 输出 | 人工判定 | 耗时 | 成本 |
|---|---|---|---|---|
| 智谱 `glm-4-flash` | 「前端开发者，熟悉 JavaScript」 | ❌ **原文零依据，编造** | 6.4s | 免费 |
| **智谱 `glm-4-plus`** | **空**（对话确实无身份信息） | ✅ **最克制** | **1.3s** | ¥0.0012/次 |
| `deepseek-v4.1-flash-free` | 「软件开发者…千余个用例」 | ⚠️ 把任务细节包装成身份 | 5.0s | 免费 |
| **`nemotron-3-super-120b`** | **空** | ✅ **好** | 43.5s | 免费 |
| `glm-4-flash`（早期版本） | 「关注记忆功能实现」 | ❌ 任务当身份 | 8.4s | 免费 |

### 关键发现

**1. 幻觉是模型能力问题，不是 prompt 问题。**

同一个 prompt，`glm-4-plus` 和 `nemotron-3-super-120b` 都能正确留空，而 `glm-4-flash` 编造了三次。加硬性反例、加三条铁律，都没能救回 flash。

**2. 「正确的克制」比「丰富的输出」更值钱。**

好模型的特征不是「写得更多」，而是**原文没有就留空**。`glm-4-plus` 把 identity 和 communication 全留空，这是正确判断——对话里确实没有这类信息。

**3. 自动化质检不可靠。**

尝试用关键词匹配做「忠实度检查」，误报率极高：
- 中文被切成「前会先检」「查相关测」这类碎片
- `win` → `Windows`、`mac` → `macOS` 的同义改写无法匹配
- 把 `nemotron` 的干净输出判成 83%

**自然语言蕴含（NLI）问题，正则和关键词匹配从原理上就解决不了。** 该检测脚本已废弃。

## 六、推荐方案

### 首选：`nemotron-3-super-120b`（免费）

- 质量已验证（与智谱 plus 同级）
- **完全免费**，保住项目「零 Token 成本」定位
- 缺点：43.5 秒较慢
- 可接受理由：记忆整理是**低频操作**（手动触发或每天一次），43 秒在用户「看预览确认」的等待中可消化

### 备选：智谱 `glm-4-plus`（¥0.0012/次）

- 速度快 33 倍（1.3s）
- 质量最好
- 成本极低（一年按每天一次算约 ¥0.44）
- 适用场景：用户嫌 43 秒太久时

### 明确排除：所有 `flash` 级小模型

编造率高，会持续污染用户画像，得不偿失。

## 七、质量保障：人工预览是唯一可靠兜底

由于自动化质检不可靠，生产实现必须包含：

1. **整理结果先预览，不直接落盘**
   - UI 展示「现有画像 → 新画像」的 diff
   - 用户确认后才写入 `memories.json`

2. **保留上一版**
   - 写入前备份到 `memories.json.bak`
   - 用户可一键回滚

3. **允许手工编辑**
   - 预览页支持直接改任意字段
   - AI 整理得不好时，用户能低成本纠正

## 附：与 GPT Dreaming 的差异

| 维度 | GPT Dreaming V3 | 本方案 |
|---|---|---|
| 触发 | 后台定期自动 | 手动 / 每日一次 |
| 数据源 | 服务端全量历史 | 本地 IDB 增量 |
| 成本 | 内部算力 | 免费模型或用户付费（约 ¥0.0012） |
| 用户可见性 | 记忆摘要页可查可改 | **预览 diff + 确认 + 可回滚**（更进一步） |
| 核心思想 | 重写而非追加 | **相同** |
